# 凭证继承统一出口，Qoder 国际版单列域名直连分流

## 背景

2026-11-02 的样本中，Qoder 国际版相关域名经部分已测 Clash 节点出现 TLS 握手失败，而直连取得 HTTP 响应；Google 授权相关路径的可达性不同。结论只覆盖当时的节点、URL 与轮次，既不代表全部节点必失败，也不代表今后永远失败。

200、401、404 分别是对应路径的 HTTP 响应；尤其 `openapi.qoder.sh` 某路径返回 404，只支持该请求链路已响应，不证明授权通过或业务成功。

## 决策

1. 出口优先级：请求级显式覆盖 > 固定凭证的出口 > CPA 全局出口。空值表示继续继承；显式直连是独立值。
2. 必要的 CPA 宿主 HTTP 桥修正用于把固定凭证出口带入这条继承链，避免插件请求漏用凭证代理。它是后端链路补齐，不涉及 CPA 认证文件卡片或管理台 UI。
3. **Qoder 国际版独立登记域名直连例外**：在受 systemd 托管的 7891 出口中，对 `qoder.sh`、`qoder.com`、`qoder.com.cn` 及其子域分流直连；其它域名保留既定上游。分流规则留在出口配置，不在插件里按供应商硬编码。
4. 国内版直连、国际版代理的账号差异由凭证配置表达；Qoder 的域名例外另外表达，二者不混为同一层。
5. 7891 的正式链路、业务和回滚验证通过后，清理临时 7899 进程并核验端口释放；这项清理继续属于交付范围。

## 后果

- 测速、签到和生产请求使用同一条代理继承链，网络例外也一致。
- 浏览器授权使用操作者浏览器的网络；插件侧轮询、带身份接口和模型调用仍需分别验收。
- 单个路径响应只算连通性证据；业务验收必须查看业务码、状态或真实回包。
- 修改运行配置后同时核验管理 API、容器文件和宿主文件；单文件 bind mount 的 inode 问题按工作区 README 的维护说明处理。
- 本 ADR 是已接受的决策，不代表实现和产品验收已完成。
